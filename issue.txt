#UPSTREAM-001 Integrate the GB MBC1 special-bank fix, verify compatibility and handle MBC1M
Former ID: #028 (historical records and commit references). Reclassified: 2026-11-07 19:25 JST.
Added: 2026-11-01 21:41:54 JST
Last updated: 2026-11-02 18:52:19 JST
Status: VERIFY (fix committed to GitHub master; post-change build and hardware re-verification pending at time of this status) / P2 / bug, gb, mbc1, test, docs
Source: The user shared a fix/verification request from another GPT chat. The initial information below was reported by that chat, not independently established in this conversation.
Original affected games: Chinese Fighter and Bomberman Quest failing MBC1 dumps.
Initial scope: GB.ino from the old Sanni CartReader ("gb.ino" in the request); porting to the new OSCR is separate.

Shared explanation of the defect:
- Some ordinary MBC1 1MB ROM dumps did not match reference CRCs.
- The old register sequence was reportedly as follows; selecting a bank whose low five bits are zero directly in the upper ROM window maps it to another bank:
  writeByte_GB(0x6000, 0);
  writeByte_GB(0x4000, currBank >> 5);
  writeByte_GB(0x2000, currBank & 0x1F);
- Example: requesting bank 0x20 yields 0x21. Check the actual current code and applicability before generalizing.

Shared successful fix approach:
- Ordinary banks: mode 0, read from 0x4000-0x7FFF.
- Special banks 0x20/0x40/0x60: switch to mode 1, choose the high bank and read from 0x0000-0x3FFF.
- Preserve ROM bank order in the output. Do not conceal mismatches by filling unreadable regions with FF.
- Ordinary MBC1 and MBC1M were said to map upper register bits differently (ordinary bits 5-6, MBC1M bits 4-5); compare this claim against the specification and code.

Shared hardware results and unknowns:
- Ordinary MBC1 1MB: The revised build reportedly dumped successfully with matching CRC; not proof of compatibility with every MBC1.
- MBC1M Bomberman Collection: Revised build reportedly dumped successfully and the user confirmed CRC equality with the reference ROM (added 2026-11-01 21:50:52 JST). This corrects an earlier note saying CRC verification was pending. It does not prove compatibility across all MBC1M titles.
- Reportedly this was not a new dedicated MBC1M mapping implementation. The reason for success and actual bank ordering/content remain uninvestigated.
- Momotaro Collection is a possible test title; do not mark it verified.
- Specific CRC/SHA values, original/full modified files and exact build versions were not supplied. Snippets of the changed code and existing MBC1M branch were subsequently shared (below). There is no documented result mapping for each of the two initially affected titles.
- No definite evidence that Retro Freak cannot dump these cartridges; do not conflate its behavior with CartReader.

Work originally proposed after approval (historical plan; do not treat as current pending authorization):
1. Compare actual source files and full diff; preserve the already successful fix.
2. Trace MBC1 bank register settings, reading windows, ROM output order and write operations.
3. Preserve ordinary MBC1 at <=512KB; inspect special banks on >=1MB titles.
4. Report read behavior at boundary banks 0x00/0x01/0x1F/0x20/0x21/0x3F/0x40/0x60.
5. Compare MBC1M wiring/bank order and modified behavior; investigate Bomberman Collection success.
6. Add a dedicated MBC1M path only if necessary; when headers cannot reliably identify it, choose an approach that does not break valid ROMs.
7. Do not alter MBC2/MBC3/MBC5 or perform unrelated refactoring.
8. Check compilation and boundary cases, distinguishing software verification from hardware results.

Addendum/correction of earlier explanation (2026-11-01 21:58:29 JST):
- Another GPT reportedly compared original and patched gb.ino, finding only one ordinary-MBC1 bank-selection change near line 1269.
- The earlier claim that original code lacked MBC1M-specific handling was corrected: both original and patched versions reportedly contain an unchanged branch for romType == 0x101 || romType == 0x103.

- The following are supplied excerpts, not full source. This chat did not independently verify that there was only one change.

Shared pre-fix diff excerpt (ordinary MBC1 else):
  writeByte_GB(0x6000, 0);
  writeByte_GB(0x4000, currBank >> 5);
  writeByte_GB(0x2000, currBank & 0x1F);
Shared post-fix excerpt (ordinary MBC1 else):
  if (currBank == 0x20 || currBank == 0x40 || currBank == 0x60) {
    writeByte_GB(0x6000, 1);
    writeByte_GB(0x4000, (currBank >> 5) & 0x03);
    writeByte_GB(0x2000, 0);
    romAddress = 0x0000;
    endAddress = 0x3FFF;
  } else {
    writeByte_GB(0x6000, 0);
    writeByte_GB(0x4000, (currBank >> 5) & 0x03);
    writeByte_GB(0x2000, currBank & 0x1F);
    romAddress = (currBank == 1) ? 0x0000 : 0x4000;
    endAddress = 0x7FFF;
  }
Shared existing MBC1M handling (unchanged by the fix):
  else if (romType == 0x101 || romType == 0x103) {
    if (currBank < 10) {
      writeByte_GB(0x4000, currBank >> 4);
      writeByte_GB(0x2000, (currBank & 0x1f));
    } else {
      writeByte_GB(0x4000, currBank >> 4);
      writeByte_GB(0x2000, 0x10 | (currBank & 0x1f));
    }
  }
Future comparison points: The existing currBank==1 loop reading 0x0000-0x7FFF, restoration of the ordinary window after special banks, endAddress termination semantics and MBC1M detection.
Preserve currBank < 10 exactly as shared; do not guess alternative values or behavior.
Policy: Preserve the successful fix, and do not change ordinary banks, existing MBC1M or other MBC types without demonstrated need.

#001 Cancellation is displayed as "SD operation failed"
Added: 2026-11-01 21:13:34 JST
Last updated: 2026-11-03 14:41:34 JST
Status: CLOSED / P2 / bug, browser
Source: User report, reproduced with PC88b + PC88a.
Reproduction: Cancel an SD copy.
Observed: The partial ROM is removed; however, a "request failed" follows "copy cancelled" and the UI reports failure.
